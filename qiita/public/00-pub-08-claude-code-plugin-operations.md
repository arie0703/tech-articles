## はじめに

こんにちは！カンリー SRE チームの有村です。

カンリーの SRE チームでは、Claude Code の **共通プラグイン（以下 sre-plugin）** を作成し、DB のトラブルシューティングやログ調査、Terraform のコーディング・セルフレビューといったインフラ運用を支援するスキルをエンジニア組織全体に提供しています。

社内向けプラグインのような共通の仕組みは、作ること自体は簡単ですが、継続的にメンテナンスしていくのは難しいものです。

本記事では、2026 年 3 月に sre-plugin を立ち上げてから現在に至るまでの運用の軌跡と、**AI を活用した「スキルの棚卸し」と「利用状況の分析」の仕組み** について紹介します。

## TL;DR

- SRE チームがインフラ運用支援スキルを Claude Code の共通プラグイン（名称: `sre-plugin`）として組織に配布し、継続的に改善している
- Claude Code の利用ログ（OpenTelemetry）を BigQuery に蓄積し、**Devin Automation で毎週** スキルの利用状況を集計・分析して Slack にレポートしている
- **10 週間利用がないスキル** は棚卸し対象とし、**Jev（OpenRouter Decisions API）** で「削除 / 継続 / 明示起動化 / プロジェクトスコープへ移動」を判定、Issue 起票と Slack 通知まで自動化している
- 利用状況を見ていくと、開発者がどんな作業に Claude Code を使っているかがわかり、**インフラ運用の課題やニーズを発見するきっかけ** にもなる

## [前提] sre-plugin について

sre-pluginという名称で、社内のエンジニアを対象に共通で利用可能なプラグインを公開しています。エンジニアはプラグインをインストールするだけで、SRE が日々の運用で培ったノウハウをスキルとして利用できます。

現在は 30 程度のスキルを提供しており、代表的なものは以下のとおりです。

| カテゴリ | スキル例 | 内容 |
| --- | --- | --- |
| DB トラブルシューティング | `aurora-troubleshoot` | CloudWatch Metrics / Logs から Aurora の性能劣化の仮説を立てる |
| ログ調査 | `cloudfront-access-log-analysis` / `waf-log-analysis` | Athena を用いたCloudFront/WAFログの検索・集計・攻撃判定 |
| CI 調査 | `gha-failure-analysis` | GitHub Actions の run-id から失敗原因を分析する |
| Terraform | `terraform-preflight-review` | Terraform PR作成前のセルフレビュー |
| コスト分析 | `aws-cost-analysis` | AWSのコスト推移と異常検知 |

「SRE に聞かないとわからない」「SRE しか知らない手順」をスキルとして切り出しておくことで、開発者が自律的にインフラの調査や変更を進められる状態を目指しています。

## 運用の軌跡

### 立ち上げ期：とにかく作る

立ち上げ当初は、SRE チーム内で繰り返し発生していた作業や問い合わせを中心に、スキルを次々に追加していきました。日次・週次のアラートレポート、ログ調査、コスト分析など、「これがあったら便利そう」というものを積極的に実装していきました。

### 拡大期：スキルが増えることによる課題

スキルが増えるにつれて、次のような課題が見えてきました。

- **似た役割のスキルが並立する**
  - 例: 日次と週次のアラートレポートが別スキルになっていた
- **特定のリポジトリでしか使わないスキルが全員に配布されている**
- **ほとんど使われていないスキルが残り続ける**

使われていないスキルが一覧に残り続けると、目的のスキルを探しにくくなるうえ、他スキルの発火判定のノイズにもなります。ここで、作って終わりではなく継続的に手入れする必要性を感じ始めました。

### 整理期：統合・移動・削除

そこで、スキルの統合・スコープ変更・削除を行うようになりました。

実際に行った整理の例は以下のとおりです。

- Datadogの週次 / 日次アラート集計のスキルが2つ存在しており、それらを統合
- AWS セキュリティグループの棚卸しをするスキルがあったが、SREチーム内でのみの利用かつ利用頻度も少ないため、SRE チームのリポジトリ配下のスキル（プロジェクトスコープ）へ移動
- 設計ベストプラクティスと実際の実装のギャップを計測するスキルを作ったが、使い所がなく長期間使われなかったため、削除

当初はチーム内でプラグインの利用状況を週次で確認し、しばらく使われていないスキルに関しては感覚的に判断して棚卸しをしていました。

しかしスキルが増えるにつれ、毎回判断すること自体が手間になってきたため、利用状況の可視化と棚卸しの判定そのものを AI で自動化することにしました。

## 仕組みの全体像

全体の流れは以下のとおりです。

```text
[Claude Code (各開発者 / CI)]
   │ OpenTelemetry
   ▼
[BigQuery: Claude Code の利用ログ]
   │
   ▼
[Devin Automation: 毎週月曜 09:00 JST]
   ├─ ① BigQuery とリポジトリのスキル一覧を突き合わせて集計（数値はスクリプトで確定）
   ├─ ② 10 週以上使われていないスキルの扱いを Jev で判定
   ├─ ③ 棚卸し Issue の起票 - 判定が「削除 / 明示起動化 / スコープ移動」のものを sub-issue として起票
   ├─ ④ 所見の作成 Devin が集計結果から示唆を最大 3 点書く
   └─ ⑤ Slack に親投稿 + スレッド（棚卸し表 / スキル別表）を投稿
```

数値の集計は決まったクエリで再現できるためスクリプトで確定させ、その結果をもとにした分析・判断だけを AI に任せています。

### 利用ログの収集

Claude Code は OpenTelemetry によるテレメトリ出力に対応しており、スキルが起動されると `claude_code.skill_activated` というイベントが記録されます。これを BigQuery に蓄積しておき、`plugin.name = 'sre-plugin'` で絞り込むことで、スキル単位・利用者単位の利用状況を集計できます。

https://docs.anthropic.com/en/docs/claude-code/monitoring-usage

例えば、スキル棚卸し判定に使う「スキルごとの最終起動日」は以下のようなクエリで取得しています。

```sql
-- 直近 12 週のスキルごとの最終起動日と起動回数
select
    json_value(attributes, '$."skill.name"') as skill_name
    , max(date(timestamp, 'Asia/Tokyo')) as last_active_date
    , count(1) as use_num
from
    `<project>.<dataset>.claude_code_logs`
where
    timestamp >= timestamp(date_sub(@week_start, interval 77 day), 'Asia/Tokyo')
    and timestamp < timestamp(date_add(@week_start, interval 7 day), 'Asia/Tokyo')
    and body = 'claude_code.skill_activated'
    and json_value(attributes, '$."plugin.name"') = 'sre-plugin'
group by
    1
order by
    1
```

## 不要なスキルの棚卸し

### 棚卸し対象の抽出

直近 12 週の利用ログから、**最後に利用されてから10週間以上経過したスキル** を棚卸し対象とします。

### Jev による判定

棚卸し対象になったスキルの扱いは、**Jev**（OpenRouter の Decisions API で提供されている判定用モデル `typesafe/jev-1.13`）に判定させています。Jev は、判断材料（state）と判定基準つきの質問（questions）を渡すと、選択肢ごとの確率を返してくれるモデルです。

判定の選択肢は次の 4 つです。

| 判定 | 意味 | 対応 |
| --- | --- | --- |
| 削除 | 需要が見込めない、または他スキルと役割が重複している | スキルを削除する |
| 継続 | 日常的に使われる見込みがあり、description の改善や周知で回復しそう | そのまま残す |
| 明示起動化して継続 | 障害対応・定期作業など出番が限定的で、自動発火の必要がない | `disable-model-invocation: true` を付ける |
| プロジェクトスコープへ移して継続 | 特定のリポジトリでしか使わない | 該当リポジトリの `.claude/skills/` へ移す |

「使われていない = 削除」と単純に決めるのではなく、**「出番が限定的なだけで、しばらく未使用でも正常なのか」「特定プロジェクト専用なのか」** という観点を判定に組み込んでいるのがポイントです。実際の質問定義は以下のようになっています（抜粋）。

```python
QUESTIONS = {
    "decision": {
        "type": "choice",
        "instructions": (
            "棚卸し対象の sre-plugin スキルをどう扱うべきか。利用実績・説明文・"
            "他スキルとの役割の重なりから判断する"
        ),
        "criteria": {
            "delete": "削除する: 導入以来ほぼ使われず需要も見込めない、または他スキルと役割が重複している ...",
            "keep": "そのまま継続する: 日常的に使われる見込みがあり ...",
            "keep_explicit_only": "明示起動専用にして継続する: 障害対応・定期作業・破壊的操作など出番が限定的 ...",
            "keep_project_scope": "スコープをプロジェクトに変更して継続する: 特定のリポジトリ・プロダクトでしか使わず ...",
        },
    },
    "future_demand": {"type": "score", "instructions": "このスキルが今後使われる見込みはどの程度か", ...},
    "overlaps_other_skill": {"type": "noul", "instructions": "他のスキルと役割が重なり、発火がそちらに吸われている疑いがあるか", ...},
    "situational_use": {"type": "noul", "instructions": "出番が限られているだけで、しばらく未使用でも正常といえるスキルか", ...},
    "project_specific": {"type": "noul", "instructions": "特定のリポジトリ・プロダクトに閉じた用途のスキルか", ...},
}
```

`decision` で 4 択の判定を、それ以外の質問で判定の根拠となる指標（今後の需要・他スキルとの重複・出番の限定性・プロジェクト専用度）を返してもらい、レポートと Issue に記載しています。

### Issue 起票と Slack 通知

判定が「削除 / 明示起動化 / プロジェクトスコープへ移動」のスキルは、Devin が親 Issue `【sre-plugin】スキル棚卸し` の sub-issue として自動で Issue を起票します。すでに sub-issue が存在するスキルは「対応済み」として扱い、毎週同じスキルが重複して起票・通知されないようにしています。

Slack には、棚卸し対象のスキルを表形式でスレッドに投稿します。

```text
棚卸し対象（10 週以上発火 0）

| スキル           | 連続0週 | 最終利用日 | 判定                      | 確率 | Issue |
| ---------------- | ------- | ---------- | ------------------------- | ---- | ----- |
| xxxx-analysis    | 12+     | -          | 削除                      | 76%  | #123  |
| yyyy-generator   | 10      | 2026-08-31 | 明示起動化して継続         | 58%  | #124  |

判定は Jev（参考値）。最終判断は人が行う。
```

この仕組みを導入してから、実際にいくつかのスキルが削除されました。棚卸しが「誰かが気づいたらやる」ものから「毎週自動で候補が上がってくる」ものに変わったことで、スキル一覧を健全に保ちやすくなっています。

## 利用状況の分析

棚卸しと同じ Devin Automation のセッションの中で、週次の利用状況の分析も行っています。Slack の親投稿には次のようなサマリを載せています。

```text
📊 sre-plugin 週次レポート（MM/DD〜MM/DD）
• 発火 N（前週比 ±N）うち CI N ／ 利用者 N 名（±N）／ 利用スキル N/N
• 経路: 自律 N%・明示 N%
• Top: skill-a N / skill-b N / skill-c N
• 棚卸し対象 N 件 → スレッド参照

所見
• （最大 3 点・各 1 文）
```

スレッドにはスキル別の発火数・前週比・利用者数・起動経路（自律発火 / 明示起動 / ネスト）を表で投稿しており、どのスキルがよく使われているか、新しく使い始めた人・使わなくなった人がいるか、といった傾向を毎週確認できます。

## 利用状況から見えてくるインフラ運用の課題

利用状況の分析を続けていると、スキルの利用ログから「開発者がどんな作業をしているか」が見えてきます。

例えば、ある特定のチームで GitHub Actions の失敗ログを調査するスキル（`gha-failure-analysis`）が多く呼び出されていることがわかりました。これは、**そのチームの CI が頻繁に失敗しており、調査に時間を取られている** 可能性を示しています。スキルのおかげで調査自体は楽になっているかもしれませんが、根本的には CI の安定性に課題がありそうです。

このように、利用状況から次のような示唆が得られます。

- **特定のスキルが特定のチームで多用されている** → そのチームの領域に構造的な課題があるかもしれない（CI の不安定さ、特定の DB の性能問題など）
- **調査系のスキルが特定の時期に集中して使われている** → 障害やリリースなど、何らかのイベントがあった可能性がある
- **利用者が増えているスキル** → 開発者のニーズが高い領域なので、さらに機能を拡充する価値がある
- **用意したのに使われないスキル** → ニーズの読み違い、もしくは周知・description の改善余地がある

SRE チームとしては、こうした傾向をきっかけに該当チームへヒアリングしたり、スキルの改善だけでなく **基盤側の改善（CI の安定化、監視の見直しなど）** に取り組んだりできます。スキルを提供し利用状況を分析することが、開発者の困りごとを把握するきっかけにもなっています。

## おわりに

本記事では、Claude Code の共通プラグインを作って終わりにせず、AI を活用して利用状況の分析とスキルの棚卸しを継続的に行う仕組みを紹介しました。
